# Offline cohort data contract

`StatCompass/Data.lua` is deliberately empty. The schema is a validation framework, **not** an authenticated provider or a license to ship data. See the [full source research](top50-eu-source-research.md) and [rights summary](provenance.md).

Schema 3 uses numeric `interface` (`120100` at the researched snapshot) **separately** from numeric `clientBuild` (`69933`). Runtime comparison uses `GetBuildInfo()` returns 4 and 2 respectively, plus `UnitLevel("player")`. The manifest has integer UTC epochs `collectedAt`, `observedAt`, `expiresAt`, an HTTPS `sourceURL`, and a reviewed `permission` reference. The unmodified source export is supplied separately; its SHA-256 is computed into `rawSHA256`. Text with control characters or surrogates is rejected before Lua 5.1 serialization.

Each cohort declares `region: "EU"`, `mode: "mythic"` (Mythic+ is the only mode; Blizzard publishes no per-player raid ranking), spec ID, matching interface/build/level, `season`, `rankingMetric`, `difficulty`, `partition`, `unit: "percentPoints"`, `semanticKind: "masteryEffectPercent"`, `observedAt`, `selectedCount` and `validCount` equal to the number of observations, and 20 to 50 unique observations ordered by rank 1–n. The Blizzard generator ships 30 per spec. Each row repeats its region, mode, spec, interface, build, level, unit, semantic kind, and observation time. Each stat percentage must be finite and nonnegative; Crit is at most 100 because it is a probability. Mastery effect may exceed 100. Each row also carries raw combat ratings `critRating`, `hasteRating`, `masteryRating` and `versatilityRating` (finite, nonnegative). Ratings are compared only rating to rating within the same spec, build and level; nothing converts them to percent. A cohort `unit` other than `percentPoints` is still rejected. There is no invented 4000-rating cutoff.

Optional per-cohort fields: `heroMix` maps hero talent tree names to how many of the cohort's players use them (counts are positive and sum to at most the cohort size). Optional `heroCohorts[specID][heroTreeID][mode]` hold cohorts restricted to one hero talent tree; each repeats `heroTreeID` and a nonempty `heroTreeName` and is validated like any cohort. The runtime reads the player's tree with `C_ClassTalents.GetActiveHeroTalentSpec()`, prefers a matching hero cohort, and otherwise uses the specialization cohort. The target carries `heroTreeID`, `heroTreeName` and `heroMix`.

`A.Snapshot()` retains `snapshot.ratingComparison[stat]` as auxiliary producer metadata, unused by the current UI: `currentRating` from `GetCombatRating` (crit = max of IDs 9/10/11, haste = max of 18/19/20, mastery 26, versatility 29), `reference = {minRating, meanRating, maxRating}` and `sampleCount` from the selected cohort, and `sourceStatus = "verified"`. The axis is a display scale, not a game cap: `axisMaxRating` is the larger of the cohort maximum and the player's own rating, plus 10 %, rounded up to 50, with that rule as `axisProvenance`. Without a valid cohort only `currentRating` is supplied (`sourceStatus = "unavailable"`). The reference also carries `lowRating` and `highRating`, the nearest-rank quartiles (ranks ⌈n/4⌉ and ⌈3n/4⌉), so the middle half of the cohort can be drawn as a band; min and max are single players and often outliers.

The auxiliary share comparison is also retained; its dynamic axis does not drive the current UI. Because absolute ratings scale with item level, the target also has `share[stat] = {mean, min, max, low, high}`: each row's rating as a percent of that row's four secondary ratings. `snapshot.shareComparison[stat]` mirrors `ratingComparison` in budget shares: `currentShare` (own rating / own four ratings, only when all four are readable), `reference = {minShare, meanShare, maxShare, lowShare, highShare}`, `sampleCount`, `sourceStatus`, and an `axisMaxShare` of max(cohort maximum share, own share) + 10 %, rounded up to 5 and capped at 100. In season 18, Protection Paladin budgets span 2,812–3,056 rating while the split varies widely: the top 30 do not form crisp build clusters (silhouette about 0.3), they vary around one direction.

**Rating targets.** `snapshot.ratingTarget[stat]` drives the current UI numbers, status and bars: the cohort's median rating (`targetRating`) with its 40th and 60th percentile (`lowRating`, `highRating`), the player's `currentRating`, `sampleCount`, `sourceStatus`, and `targetPercent` (the cohort's median percentage, for the tooltip). Targets compare rating with rating: `GetCombatRating` in game and Blizzard's `rating_normalized` are both pure gear rating. An earlier version converted the cohort's percentages with the player's live conversion; live percentages include buffs the logged-out API profiles never have (Mark of the Wild alone is +3 % versatility), which pushed targets far too low, so it was dropped. The current producer omits `personal`. `ratingTarget.totals = {targetRating, ownRating}` shows whether the four targets fit the player's budget. Guardian, season 18: crit 914, haste 1,193, mastery 434, versatility 386.

**Priority.** `target.priority` lists the four stats by the cohort's median budget share, highest first, ties in Character-window order. It says where top players invest their secondary budget, not a simulated stat weight. Blizzard's API hero tree IDs equal the in-game sub-tree IDs: `C_ClassTalents.GetActiveHeroTalentSpec()` returned 66 on a Master of Harmony Mistweaver, the API's ID for Master of Harmony.

Observation chronology is bounded twice: every row must be observed within the 24 hours ending at its cohort `observedAt`, inclusive, and no more than 30 days before dataset `collectedAt`, inclusive. Cohort `observedAt` equals the latest row observation; dataset `observedAt` equals the latest cohort observation. The builder and runtime both reject stale rows or inconsistent summaries. A provider may require a shorter observation age. These schema limits are not proof that a source is current or licensed.

The offline builder rejects future collection or observation timestamps, expired data, and an expiry more than 30 days after collection. The runtime requires finite integer `GetServerTime()`, rejects unknown time, future collection/observation, expiry at or before the current second, and exact build/interface mismatch. A provider's permitted cache life can be shorter than 30 days; the schema's maximum does not override it. The output carries source, selected/valid counts, observed/collection/expiry dates, and ranking metadata into the target object and panel tooltip. The target exposes, per stat, the arithmetic mean, the exact minimum and maximum, and the nearest-rank middle 50% band (ranks ⌈n/4⌉ and ⌈3n/4⌉) of the percentages, plus `target.rating[stat] = {mean, min, max}` for the ratings, and `sample = n`. These describe selected players; they are not an optimum.

The visible panel schedules one refresh at the validated expiry; hiding, a newer render, or a change in dataset identity, mode, or spec invalidates that callback. It does not poll while hidden. In combat, expiry clears references immediately using the last current-value sample, without reading stats or rebuilding targets. A shown tooltip is refreshed with the panel. Overflow-safe mean calculation keeps finite percentage inputs finite, and large or tiny nonzero display values use compact scientific notation. Each row shows current and target ratings, with a white target marker and a P40–P60 band. Without a valid target, only readable current ratings remain; target labels and bars are hidden. The interface escapes WoW markup in displayed source, ranking metadata, and specialization names.

## Combat refresh and cache lifecycle

The existing `Snapshot`, `GetTarget`, `ValidateDataset`, `ReadHeroTree`, `Flush`, `QueueRefresh` and `SetVisible` interfaces remain available. Rating/percentage semantics are unchanged. The UI must route refreshes through `QueueRefresh`/`Flush`; `Snapshot` is a synchronous read only outside combat, and a defensive frozen-copy accessor during combat.

- `snapshot.preCombat` is an additive boolean. It is `true` only for a frozen, readable out-of-combat sample displayed during combat. The UI labels that state **Stand vor Kampf** (English: **Pre-combat snapshot**), even after reference expiry/invalidation. It is `false` for ordinary out-of-combat snapshots and for the neutral combat state when no readable prior sample exists. Never infer this label from combat state alone. At least one finite percentage or rating makes a sample readable; unknown individual fields stay unknown. An entirely unreadable out-of-combat read does not overwrite the private last-readable sample. Stored snapshots/ratings are private copies, not renderer-owned tables.
- `SetCombat(true)` invalidates queued callbacks and renders the frozen sample once if the panel is effectively visible and expanded. It takes no fresh percentage/rating sample. There is no ten-second timer or other periodic combat refresh. Ordinary stat events only mark pending work. Hide/collapse cancels callbacks; reopening during combat renders only the prior sample, or neutral unknown fields with `preCombat=false`. `SetCombat(false)` invalidates old callbacks and performs one immediate visible fresh refresh; while hidden it performs no scan, and the next reopen reads fresh values. Duplicate combat-state notifications are inert. This freeze policy supersedes the earlier ten-second candidate and its core-test expectations.
- Combat snapshot/refresh dispatch uses a private cache-only target check and does not call the public `GetTarget` aggregation entry point. Direct `GetTarget` calls in combat delegate to the same bounded cache-only helper, which only returns a defensive copy of an already validated precombat target. On display access it checks the dataset/header and selected-cohort identities, spec, hero ID, mode, interface, client build, player level and readable server time. The retained readable snapshot must also belong to that exact target-cache generation. Expired, changed or unreadable context removes all reference/comparison targets until an out-of-combat rebuild. Historical current values and their original spec metadata remain labelled precombat, never current measurements. There is no periodic context polling. It never validates rows, sorts observations or computes cohort quantiles in combat. Direct `ValidateDataset` calls return false in combat. Missing precombat data remains unavailable.
- Out of combat, a private exact table/value ledger checks that a cached dataset is unchanged before reusing validation and target calculations. This still traverses the source graph to preserve detection of in-place mutations; it skips repeated semantic validation, aggregation and sorting, not every source access. It is deliberately not an identity-only or hash-only memo. Nonplain/metatable or Secret-containing graphs are not reusable immutable cache entries. `ValidateDataset` itself remains uncached and fully checks explicit out-of-combat calls.
- Shipped datasets are static for a client session. A future in-session producer must call `InvalidateTarget()` before replacing or modifying published data and then `QueueRefresh()`; never mutate observation rows silently during combat. `InvalidateTarget()` discards cached validation/targets and removes visible references immediately without taking another current-stat sample. No row traversal is performed to detect silent in-place row edits during combat.
- `QueueRefresh(reason)` adds an optional event-name argument; argument-free callers remain valid. `PLAYER_SPECIALIZATION_CHANGED`, `ACTIVE_TALENT_GROUP_CHANGED`, `PLAYER_TALENT_UPDATE`, `TRAIT_CONFIG_UPDATED`, `UNIT_LEVEL` and `PLAYER_ENTERING_WORLD` invalidate context even while hidden. In combat, reference invalidation is immediate; outside combat, normal next-frame coalescing handles the render. Secret/error current values remain unknown rather than zero.

UI integration (owned by `UI.lua`): register `PLAYER_REGEN_DISABLED` and `PLAYER_REGEN_ENABLED`, forward them to `SetCombat(true/false)` and return without also queuing a refresh. Pass the event name to the existing `QueueRefresh(event)` call after its unit filters. Register `TRAIT_CONFIG_UPDATED` and `PLAYER_ENTERING_WORLD` as context events. On startup/world entry, synchronize the combat state from a guarded `InCombatLockdown()` read before attaching/showing the panel; an unreadable result must fail closed to combat mode. Keep the existing effective-visibility calls to `SetVisible` for hide/collapse. No additional `OnUpdate` or UI-owned repeating timer is needed.

All four current UI axes are fixed at 0–2000 rating. Only drawing is clamped; offscale values retain their numbers and overflow indicators, and tooltips retain the actual endpoints. This display range is not a game cap or recommended maximum. Separate user-supplied DR labels have tooltips but no bar marker or cap stroke; they do not affect targets, bands, status or scale. See the [UI integration contract](secondary-budget-shares.md) for validation, DR context and tooltip behavior. Geometry changes redraw the cached bar state without reading live stats. The panel scales its own design units from CharacterFrame's physical height, matches its physical top and bottom when it fits the viewport, and uses a compact layout for shorter frames.

For an authorized future release, generate a candidate outside the addon first:

```powershell
.venv/Scripts/python.exe tools/build_data.py --manifest reviewed-cohorts.json --raw-source unmodified-source-export.json --output candidate-Data.lua
```

The source and rights review must establish an actual EU spec ranking, snapshot/stat semantic matching, collection and observation times, provider cache and distribution permission, attribution, raw-data retention/deletion, character status/deletion handling where required, and a way to revoke stale distributed archives. The Blizzard workflow in [blizzard-acquisition.md](blizzard-acquisition.md) produces a candidate outside the source dataset. Review all selected ranks and hashes for the selected context: the current generator selects the top 30 per spec, while the validator accepts 20 to 50 observations per cohort. The repository’s `StatCompass/Data.lua` remains empty. For an authorized release, the generated candidate from a successful weekly run must pass review and release validation before it is installed in the packaging checkout (release staging), as described in [releasing.md](releasing.md). It is not a repository dataset replacement. The game performs no network requests.
